# Database Schema Changelog

Every schema change to the dev database (`DGM-LCCSRVCS` / `Concord_Practicum`) gets one row here, added at the same time the corresponding `Database\NN_Description.sql` script is written **and run**. Verified against the live database on 2026-09-15 (see the note at the bottom for what that check found).

**Rule going forward:** any time a new `Database\NN_*.sql` migration is written and applied, add a row to this table in the same change.

| Date | Script | Table(s) | Change | Why |
|---|---|---|---|---|
| 2026-08-15 | `03_Buildings_And_Units.sql` | Buildings (new), Units | Created `Buildings`; added `Units.BuildingID` (FK); renamed `UnitNumber`→`FlatNumber`; added `FloorNumber`, `BedroomCount`, `BathroomCount`, `HasKitchen`, `HasHall`, `Facing` (+ CHECK) | Units needed to belong to a specific Building instead of directly to a Project, and needed richer per-unit attributes for the listings |
| 2026-08-15 | `04_Customization_Rejection.sql` | CustomizationSelections | Added `Status` (Pending/Approved/Rejected) + `Remarks` | Let the Project Manager reject a client's customization pick, not just approve it |
| 2026-08-18 | `05_Project_Completion_Date.sql` | Projects | Added `EstimatedCompletionDate` | Needed a target completion date to show clients/admin |
| 2026-09-08 | `06_Building_Completion_Date.sql` | Buildings | Added `EstimatedCompletionDate` | Per-building completion tracking, same idea as Projects |
| 2026-09-08 | `07_Project_MaxBuildings_TotalArea.sql` | Projects | Added `MaxBuildings` + `TotalAreaSqFt` | Cap how many Buildings a Project may have and record its total footprint |

| 2026-09-14 | `12_Booking_Cancellation_And_Sold_Status.sql` | UnitBookings, Units | Added `UnitBookings.Status` (Active/Cancelled) + `CancelReason`; extended `Units.Status` CHECK to allow `Sold` | Let Admin cancel a booking without deleting history, and let Accounts flip a fully-paid Booked unit to Sold |
| 2026-09-14 | `13_Trim_To_Four_Actors.sql` | Products | Made `VendorID` nullable; added `Supplier` | Vendor accounts were removed (trimmed to Admin/Client/PM/Accounts); products are now added directly by Admin with a free-text supplier note |

| 2026-09-15 | `16_Units_AttachedBathrooms_BalconyCount.sql` | Units | Dropped `HasBalcony`; added `AttachedBathrooms` + `BalconyCount` | A plain "has balcony" flag wasn't enough info; replaced with an actual count, plus how many bathrooms are en-suite |
| 2026-09-15 | `17_Units_Drop_HasParking.sql` | Units | Dropped `HasParking` | Unit-level parking was redundant with `Buildings.HasParkingFacility`, which already says whether the building has shared parking |

| 2026-09-20 | `20_Products_Backfill_CategoryID.sql` | Products | Data only: seeds the 4 sample products with a `CategoryID` on a fresh setup; backfills `CategoryID` / `Category` / `IsApprovedForClientCustomization` on any existing product where `CategoryID IS NULL` | Products with a NULL `CategoryID` are dropped by the INNER JOIN to `MasterCategories` in `BuildCustomizeViewModel`, so the Client's Customize modal showed "No materials are on record" |
| 2026-09-20 | `22_Add_ProjectID_To_Products.sql` | Products | Added nullable `ProjectID` (FK to `Projects`); NULL = applies to all projects | Structural (non-customizable) materials such as Cement can now be specific to one Project; customizable finishing products stay global (NULL). | 2026-09-20 | `23_Add_BuildingID_To_Products.sql` | Products | Added nullable `BuildingID` (FK to `Buildings`); NULL = whole project | Structural materials can now be scoped to one Building, extending 22. The Customize modal resolves Building -> Project -> global, one product per category |
| 2026-09-20 | `24_Create_ProductScopeAssignments.sql` | ProductScopeAssignments (new) | Created junction table (ProductID, ProjectID, BuildingID; unique per product+scope) and backfilled it from `Products.ProjectID`/`BuildingID` and the currently client-visible customizable variants. `Products.ProjectID`/`BuildingID` (22/23) are kept but no longer read or written | The Project Manager, not the Admin, decides which catalog products each Project/Building offers; one catalog item must be assignable to several buildings independently, which columns on Products can't express |
| 2026-09-20 | `26_Backfill_Approved_Selections.sql` | CustomizationSelections | **Data only.** Set `Status = 'Approved'` on the 3 still-Pending selections (booking 15) of bookings that already had a recorded client payment and were selected before the Approval workflow went live (2026-09-20 10:36:40); `Remarks` notes the migration | The workflow bills only Approved customizations, which turned booking 15's balance from +5,000 into -91,000 because its selections were paid for before any approval step existed. Selections on unpaid bookings stay Pending for a PM to review; a cut-off keeps a re-run from approving new ones |
| 2026-09-20 | `27_Drop_Legacy_Objects.sql` | Products, Buildings, ProjectMilestones, Users | Dropped `Products.VendorID`, `Products.CreatedDate`, `Buildings.CreatedDate` and the `ProjectMilestones` table; deleted the 8 Vendor / Site Engineer / HR Executive users; replaced the Users.Role CHECK with `CK_Users_Role` (Admin, Client, Project Manager, Accounts Officer only) | Cleanup of the Vendor / HR / Site Engineer / procurement-era leftovers: nothing in the app read or wrote any of them, and they were confusing to anyone reviewing the code or database. Idempotent, so a fresh setup (00 .. 27) ends up identical to the live database |
| 2026-09-20 | `00_MASTER_Setup.sql` (rewritten) | all | Baseline no longer creates Vendors, Requisitions, RequisitionItems, Approvals, Employees, VendorPayments; `Products.VendorID` is a plain nullable column (no FK); `Projects` no longer pre-declares `MaxBuildings`/`TotalAreaSqFt` | Fresh-setup baseline only -- the live database was not touched by this rewrite. The old 00 already declared those two Projects columns, so `07_Project_MaxBuildings_TotalArea.sql` failed on any fresh setup; that is fixed |
| 2026-09-21 | `28_Drop_Products_ProjectID_BuildingID.sql` | Products | Dropped `Products.ProjectID` and `Products.BuildingID` (and their foreign keys) | Added by 22/23, replaced by `ProductScopeAssignments` (24, which copies their data across); the application no longer reads or writes either column |

## 2026-09-15 verification note

Checked every script above against the live dev database by querying `INFORMATION_SCHEMA.COLUMNS` / `sys.check_constraints` / `sys.tables` for each table and column listed. **Everything matched except one gap: `08_Project_Milestones.sql` and `09_Milestone_Description.sql` had never actually been run — the `ProjectMilestones` table didn't exist.** Both were applied during this check; the table now exists with all 7 expected columns (`MilestoneID`, `ProjectID`, `MonthNumber`, `IsCompleted`, `CompletedDate`, `CompletedByUserID`, `Description`). Every other script (03–17) was already correctly applied.
